Explicação em linguagem bem simples

Imagine uma casa inteligente. Ela tem um sensor, que é como um termômetro: ele olha o que está acontecendo. O DHT11 mede a temperatura e a umidade do ar.

O ESP32 é como o cérebro da casa. Ele lê o sensor, prepara a informação e consegue conversar com a Internet pelo Wi-Fi ou pelo Bluetooth. Ele é rápido e tem bastante memória. O Arduino Uno também é um cérebro pequeno: é mais simples, ótimo para aprender e controlar coisas, mas não tem Internet sozinho e tem menos memória.

Quando o ESP32 recebe uma medida, ele coloca tudo em uma mensagem organizada, chamada JSON. É como escrever: “o sensor DHT11-01 marcou 24,6 graus e 58% de umidade”.

Para enviar essa mensagem, usamos o MQTT. Pense nele como o serviço de entrega de cartas:

  • o dispositivo é o publisher: escreve e envia a carta;
  • o broker é o carteiro central: recebe a carta e sabe quem quer recebê-la;
  • o subscriber é quem assina o assunto e recebe as cartas;
  • o tópico é o nome da caixa de correio, como casa/sala01/temperatura.

Assim, o sensor não precisa conhecer cada pessoa que quer ver a temperatura. Ele só entrega ao broker, e o broker distribui.

O QoS diz o quanto queremos ter certeza de que a carta chegou:

  • QoS 0: tenta entregar uma vez; pode se perder;
  • QoS 1: garante que chegue, mas pode entregar duas vezes;
  • QoS 2: garante uma única entrega, mas dá mais trabalho e usa mais comunicação.

O Node-RED é como uma mesa de montagem com pecinhas ligadas por caminhos. O MQTT in pega as mensagens, o Function pensa e faz contas, e o MQTT out envia uma resposta ou um comando. O Dashboard mostra tudo na tela: o Gauge mostra o valor de agora, o Chart mostra o que aconteceu ao longo do tempo, o Text escreve informações, o Filter escolhe o que queremos ver, o Debug ajuda a descobrir erros e o Telegram avisa alguém quando há um problema.

A nuvem é como um grande computador na Internet. Ela pode guardar o histórico, conferir se o dispositivo é autorizado, aplicar regras e mostrar os dados em outros programas. Se alguém mandar um comando, ele volta pelo caminho contrário até o dispositivo ou atuador.

Resumo da história: o sensor mede → o ESP32 organiza → o JSON descreve → o MQTT transporta → o broker distribui → o Node-RED trata → a tela mostra ou o Telegram avisa → a nuvem guarda. Um comando pode voltar pela mesma estrada.

PRIORIDADE: ESP32 é melhor para IoT conectada por ter mais desempenho, memória e Wi-Fi/Bluetooth nativos. Uno é mais simples e adequado a aprendizagem e projetos locais. Atenção às tensões: ESP32 = 3,3 V; Uno = 5 V.

Não confunda: UART, SPI e I2C são interfaces de comunicação entre componentes; não significam conexão à Internet. A rede do ESP32 vem do Wi-Fi/Bluetooth.

2. Fundamentos de IoT

IoT integra sensores/atuadores, processamento, comunicação e serviços para medir o mundo físico, transmitir dados, tomar decisões e agir sobre o ambiente.

3. MQTT, HTTP e Pub/Sub

MQTT — PRIORIDADE MÁXIMA

MQTT é um protocolo leve de mensagens para IoT, normalmente sobre TCP/IP. Usa publicação/assinatura e é adequado a dispositivos com pouca banda, energia ou processamento.

Broker

O broker é o servidor intermediário: recebe mensagens dos publicadores, verifica assinaturas e encaminha os dados aos assinantes. Assim, sensor e aplicações ficam desacoplados.

  • Publisher: publica em um tópico.
  • Subscriber: assina um tópico.
  • Broker: distribui mensagens.
  • Tópico: endereço lógico da mensagem.

Exemplo: o ESP32 publica em casa/sala01/temperatura; dashboard e alertas assinam esse tópico.

MQTTHTTP
Pub/Sub e broker; leve para telemetria contínua; usa tópicos.Requisição/resposta; cliente acessa servidor/API; usa GET/POST.

Regra prática: telemetria e comandos entre dispositivos favorecem MQTT; integração pontual com API web costuma usar HTTP.

4. Tópicos, JSON e QoS

Padronização de tópicos — PRIORIDADE

Use hierarquia consistente com níveis separados por /: casa/sala01/temperatura, fabrica/linha2/motor07/status, predio/3oandar/umidade. Isso facilita localizar, filtrar e autorizar dados.

JSON

JSON é estruturado e legível, com pares chave/valor:

{
  "dispositivo": "dht11-01",
  "temperatura": 24.6,
  "umidade": 58,
  "timestamp": "2026-09-10T19:00:00Z"
}

Ele padroniza a troca entre microcontrolador, Node-RED, nuvem e aplicações.

QoS — PRIORIDADE MÁXIMA

NívelSignificado
QoS 0No máximo uma vez; pode não chegar.
QoS 1Pelo menos uma vez; pode duplicar.
QoS 2Exatamente uma vez; maior custo.

Memorização: 0 = pode perder; 1 = pode repetir; 2 = exatamente uma vez.

  • Azure IoT Hub: identidade, comunicação e telemetria de dispositivos no Azure.
  • EMQX: broker MQTT escalável, próprio ou em nuvem.

DHT11: sensor digital barato de temperatura e umidade relativa. É simples e econômico, porém menos preciso e veloz que sensores avançados. No fluxo, ele gera a telemetria que o microcontrolador transforma em JSON.

Node-RED é uma ferramenta visual baseada em fluxos, executada sobre Node.js.

7. Fluxo Client/Edge → Cloud Back-End

  1. Client: DHT11 mede temperatura e umidade.
  2. Microcontrolador: lê o sensor e monta um JSON.
  3. Publicação: publica o JSON em um tópico MQTT.
  4. Edge/Broker: broker recebe; Node-RED usa MQTT in.
  5. Processamento: Function valida e transforma msg.payload.
  6. Uso local: Dashboard, Gauge, Chart, Text e Filter exibem; Debug testa; Telegram alerta.
  7. Cloud: autentica dispositivo, aplica regras, armazena histórico e oferece APIs/dashboards.
  8. Controle: Cloud → broker → MQTT out → dispositivo/atuador.

Fluxo em uma linha: DHT11 → ESP32 → JSON → MQTT → Broker → MQTT in → Function → Dashboard/Alertas/Armazenamento → comando via MQTT out.

8. Perguntas que podem cair

  1. Por que o ESP32 é mais indicado para IoT? Mais desempenho, memória e conectividade nativa.
  2. Qual o papel do broker? Intermediar/distribuir mensagens.
  3. MQTT × HTTP? Pub/Sub/broker × requisição/resposta.
  4. QoS 1? Pelo menos uma vez, podendo duplicar.
  5. Para que serve o tópico? Organizar/identificar o canal lógico.
  6. Function? Lógica JavaScript para validar/transformar/encaminhar.
  7. Quem recebe/publica MQTT? MQTT in recebe; MQTT out publica.
  8. Gauge × Chart? Valor atual × evolução no tempo.

Revisão de 5 minutos antes da prova

Placas: ESP32 = dual-core, mais memória, Wi-Fi/Bluetooth, 3,3 V. Uno = ATmega328P, 8 bits/16 MHz, pouca memória, 5 V, simples e sem rede nativa.

MQTT: Publisher publica → broker intermedeia → subscriber assina.

QoS: 0 pode perder; 1 pode repetir; 2 exatamente uma vez.

Node-RED: MQTT in recebe; Function processa; MQTT out publica. Gauge = agora; Chart = histórico; Debug = diagnóstico; Telegram = alerta.

Arquitetura: DHT11 mede → ESP32 monta JSON → MQTT → broker → Node-RED → dashboard/alerta/nuvem. O comando volta por Cloud → broker → MQTT out → atuador.

Em IoT, o sensor gera dados, o microcontrolador organiza, o MQTT transporta, o broker distribui, o Node-RED processa e a nuvem armazena/coordena; comandos retornam pelo mesmo ecossistema até o atuador.
